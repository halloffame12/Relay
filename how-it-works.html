[ WORKFLOW ARCHITECTURE ]

A transfer in five deliberate beats.

From initiating a session to opening verified pages on another device, Relay prioritizes transparency, explicit user approval, and cryptographic verification at every step.

[01 / OFFER INITIALIZATION]

Generate Ephemeral QR Invitation

The receiving device starts a temporary listening session and displays a single-use QR invitation.

The QR code carries an ephemeral session token, local network IPv4 candidates, port numbers, and protocol version v2. It expires after 10 minutes and strictly rejects any replayed connection.

Technical Specifications

  • Strict payload validation (Relay binary format, never a web URL)
  • Maximum 10-minute token lifetime
  • Manual IPv4 & 6-digit code fallback for camera-restricted environments
[02 / HANDSHAKE & SELECTION]

Scan & Direct Handshake

The sender scans the code to establish an immediate, authenticated peer link.

Relay parses the QR payload, tests local network reachability, and completes a versioned hello/welcome handshake. The sender selects up to 20 documents (max 200 MiB batch) from its local library.

Technical Specifications

  • Zero manual IP or port configuration required
  • Framed control protocol: [type:1][len:4 BE][payload]
  • Only Relay-managed library items are exposed
[03 / CONSENT GATE]

Explicit Receiver Approval

No file bytes are accepted or written to disk until the recipient explicitly reviews and approves.

Before streaming begins, the sender submits a transfer offer containing the exact document title, format, byte size, and declared SHA-256 hash. The receiver presents a blocking dialog requiring conscious user consent.

Technical Specifications

  • Protects against unsolicited files and spam
  • User sees exact file name, format, and size in megabytes
  • Rejection cleanly closes the session with zero disk writes
[04 / BOUNDED STREAMING]

Streaming Bytes & SHA-256 Calculation

Bytes stream through bounded memory buffers while both sides compute cryptographic hashes.

Upon approval, the sender streams file chunks in bounded 64 KiB segments. Both devices compute the SHA-256 digest on the fly. Streaming never buffers whole files in RAM, ensuring smooth performance even on low-memory devices.

Technical Specifications

  • Bounded memory streaming prevents out-of-memory crashes
  • Real-time speed, bytes received, and percentage calculation
  • Interrupted connections immediately trigger cleanup of temporary .part files
[05 / INTEGRITY & COMMIT]

Verification & Library Import

The receiving device verifies the declared size and SHA-256 hash before committing the file.

Once all bytes arrive, Relay checks that the received hash matches the sender's declared manifest. The verified temporary file is then imported into the local Drift SQLite database, and the single-use invitation token is destroyed.

Technical Specifications

  • Bit-for-bit integrity validation via SHA-256
  • Duplicate file detection prevents redundant disk usage
  • Tokens automatically rotated; old codes cannot be reused
[ NETWORK TOPOLOGY ]

Direct first. Relayed when needed.

How Relay navigates different network environments without requiring you to understand IP tables or port forwards.

[ PRIMARY PATH ]

Direct LAN Socket

When both devices share the same Wi-Fi router or mobile hotspot, Relay establishes a direct, high-speed TCP socket over the local network.

  • Speed: Full local Wi-Fi bandwidth (often 15–40+ MB/s).
  • Privacy: Data packets never leave your local physical router.
  • Zero Internet: Operates even during complete internet outages.
[ FALLBACK PATH ]

Cross-Network WebRTC Relay

When devices are on different networks (e.g. mobile cellular vs home broadband, or strict AP isolation), Relay falls back to WebRTC data channels via an authenticated signaling server.

  • Encryption: WebRTC data channels are strictly DTLS-encrypted end-to-end.
  • Ephemeral Sessions: TURN credentials are minted per-session and expire quickly.
  • Honest State: Requires deployed signaling service; app reports status clearly.
[ RESILIENCE & INTEGRITY ]

What happens when a transfer is interrupted?

Zero orphan files, zero broken database records, and zero ambiguous states.

01

Immediate Clean-Up of Partial Files

If the Wi-Fi drops, battery dies, or the user cancels midway, Relay immediately purges the temporary `.part` file from disk. No phantom files occupy your phone storage.

02

Atomic SQLite State Updates

Drift SQLite transactions only record a transfer as "completed" after full SHA-256 validation passes. An interrupted transfer is marked failed and never presented as readable.

03

Brute-Force Guard on Manual Codes

If manual 6-digit pairing is used and 5 consecutive incorrect attempts occur, the receiver immediately rotates the session token, invalidating previous guesses.

04

Malformed Data Rejection

JSON control frames nested deeper than 32 levels or containing unescaped bidi/control characters are rejected before parsing to prevent parser exploitation.
